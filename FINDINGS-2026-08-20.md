# Findings 2026-08-20: the minimal tree does NOT recover — full catastrophe reproduces here

New evidence gathered against the three live deployments (same commit) plus local
`vercel build` A/B diffs. Two corrections to this README and one sharpened verdict.

## 1. The README undersells the severity — the infinite loop reproduces in THIS tree

The README says the minimal tree "still recovers and mounts the modal" and that the
freeze "needs at least one more production ingredient". As of today (eve 0.40.0 build,
next 16.3.1, deployments fresh), **no extra ingredient is needed**:

- Open `/en/lab` on BROKEN, touch nothing: the router enters an **infinite prefetch
  loop** — 684 requests in ~15 s, 1,627 within a minute, sustained ~40 req/s, re-fetching
  the three card URLs forever. CONTROL issues exactly 6 prefetches and stops.
  Every looped request is a billable function invocation.
- Clicking a card mounts the modal **with a corrupted param**: `useParams()` delivers
  `slug = "(.)sudoku"` — the interception marker leaks into userland — while the loop
  continues and the catalog page unmounts.

Note: next 16.3.1 *contains* the prefetch-loop fix (vercel/next.js#97128). It cannot
help here because it assumes a refetched `/_tree` reflects the server's real routing;
the services router violates that on every request, re-arming the loop each cycle.

## 2. The mechanism is sharper than "$segmentPath is not substituted"

Captured on BROKEN via headless-Chrome network inspection (prefetch of
`/en/lab/encyclopedia` issued from `/en/lab`):

```
x-matched-path:          /[locale]/lab/(.)[slug].rsc
x-nextjs-rewritten-path: /en/lab/(.)(.)encyclopedia.rsc      <- interception rewrite applied TWICE
tree param:              slug = "(.)encyclopedia"
```

CONTROL, same request: `x-nextjs-rewritten-path: /en/lab/(.)sudoku` (single marker,
clean param). And `/_tree` probes against prerendered dynamic routes return params like
`locale = "%5Blocale%5D.segments"`, `rest = "_tree.segment"` — i.e. the router DID
substitute `$segmentPath`, built the bracketed artifact path
`/[locale].segments/_tree.segment.rsc`, URL-encoded it, and re-matched it as an ordinary
page URL instead of serving the artifact.

Coherent theory covering both captures: the V2 services router **re-runs or mis-orders
the route-chain phases** (`continue`/`check`/`override` semantics) rather than merely
dropping one substitution.

## 3. Build Output A/B proves the builder and eve's write are not the live defect

`vercel build` (CLI 59.1.4, @vercel/next 4.21.6) locally, `USE_EVE=0` vs `USE_EVE=1`:
Next's 46-route table is **byte-identical** (modulo build hashes) in both outputs,
including the `$segmentPath` has-capture route, correctly ordered. The eve build adds
exactly one route (`^/eve/agents/demo/eve/v1/(.*)$ -> service eve-demo`) plus top-level
`services` + `experimentalServicesV2` keys. The platform merge pipeline (fixed July 2026
in vercel/vercel#16889 + #16938) does its job; the *runtime router* is what diverges.

Ownership triangulation (six-agent source sweep of vercel/eve, vercel/vercel,
vercel/next.js — details in the full report):

- **Vercel platform owns the bug.** `has`-captures→dest substitution is first-class,
  schema-validated, tested, and e2e-probed in routing-utils — but only on deployments
  *without* `services`. Declaring services "activates V2 routing" (CLI comment), a
  closed-source router mode with zero test coverage for this route shape. `vercel dev`'s
  reduced services router doesn't evaluate `has` at all and substitutes unknown `$name`
  as empty strings. Sibling open issues with the same works-standalone-breaks-under-services
  signature: vercel/vercel#16924, #16915, #16296/#16298 — all filed within three weeks of
  the services public beta (2026-06-30).
- **Eve owns the trigger, and cannot fix the router.** Its Next integration is
  byte-identical 0.33.3→0.42.0 (md5-verified); structurally no eve code can run after
  @vercel/next (unlike its SvelteKit/Nuxt integrations which merge post-framework), so
  "write later" is impossible. Its unilateral escape is embedded mode (vercel/eve#1094).
- **Next.js owns hardening only.** In minimal mode it explicitly delegates
  header→artifact-path translation to the platform router (base-server.ts:552-565); its
  client validates `/_tree` responses only for build ID + decodability, so a
  wrong-but-parseable catch-all tree passes every guard, gets cached, and (no `Vary:
  Next-Url` on the wrong page) is re-keyed for all referrers — which is why interception
  can never mount. The separate optimisticRouting misprediction
  (vercel/next.js#96893) is a real Next.js client bug with a different fix
  (per-route opt-out — promised, not landed; community PR #97340 closed unmerged).

## 4. The old repro's 404 era is over — both failure modes converged

`eve-segment-prefetch-repro` (old, `/static`): today returns 200-with-wrong-tree, same as
this repro (its README's `x-matched-path=/404` no longer occurs; its literal artifact
path + router headers now 500s with `_global-error`). The "eve >= 0.39.1 partially fixed
the tree responses" claim has no corresponding eve code change (integration byte-identical
across that range) — that shift was a platform-side change.
